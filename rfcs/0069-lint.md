# RFC 0069: `knave lint`

**Status:** Proposed
**Date:** 2026-11-11

## Problem

A program can bind a name that nothing reads, write `(if c true false)`, or grow a function past what a reader can hold in mind, and the compiler says nothing. Rustc's own lints never reach the user, because `knave build` passes `--cap-lints allow`. The compiler prints six warnings today, and no user can silence any of them:

- L0434: an unreachable `match` arm, from `types`.
- L0504: a function that changes an argument but whose name lacks `!`, from `ownership`.
- L0217, L0249, L0251 and L0256: a second Rust path for one trait, a macro input set aside, a library that hides a local module, and a test module that hides a source module, all from `expand`.

Q-b under Recommendation asks which of them a user can silence.

The language needs a command that runs style and correctness checks, written in knave where knave can express them, with one way to silence each check.

## Options

Each option runs after expansion and reads only the `Program` that `Expander::expand` returns. The options differ in the form in which a rule receives the expanded program.

The example is the first rule, `unused-binding`:

```lisp
(defn area (width height)
  (let (unused (+ width 1))
    (* width height)))
```

Every option prints the same warning:

```text
warning[L0801]: `unused` is never read
 --> area.knv:2:9
  |
2 |   (let (unused (+ width 1))
  |         ^^^^^^ bound here and never read
  |
  = help: remove the binding, or name it `_unused` to keep it
```

### Read-back forms

The `lint` stage turns each definition of the program's modules back into kernel forms:

```lisp
(def area (fn (width height) (do (local unused (add width 1)) (mul width height))))
```

The stage gives each binding one fresh scope that no expansion used, and puts that scope on every symbol that names the binding, so the existing `same-binding?` compares two symbols by the binding that expansion resolved. A kernel form's head names no binding.

The Rust read-back already visits every node, so it hands each definition to the rules as a flat table, one entry per node. An entry holds the node's head symbol, its span, its parent's index and its depth. A symbol's entry also holds its binding identity and whether it binds or reads. A rule is a plain knave function that iterates over the table with `loop` and `recur`, so no knave code recurses over the tree.

### Forms captured during expansion

The expander records every form at the moment it becomes a kernel form, with its scopes, and the rules read that record.

```lisp
(local unused (+ width 1))
```

The forms keep the user's names. But `same-binding?` needs the expander's binding table, which `Program` does not hand out after expansion, and the capture changes the expander.

### A data view of the core IR

The interpreter gains a value that wraps a node of the core IR, and built-ins such as `core-kind`, `core-children` and `core-binding` that read it.

```lisp
(core-kind node)
```

The view loses nothing, but it adds a value kind and about six built-ins to the interpreter, which the RFC 0063 interpreter must carry too. Rules would also read a second shape of code that no macro uses.

## Recommendation

Read-back forms.

- **Small compiler, big prelude.** Rules stay knave code in `prelude/lint`. The Rust side only reads, converts and reports.
- **Few rules, no exceptions.** A rule reads forms, the one data type for code, with the built-ins a macro uses, and `same-binding?` keeps its meaning.
- **Every accepted program lints.** No knave code recurses over the tree, so the walk has no limit tied to nesting or width.
- **User experience first.** A rule sees what `knave expand` prints, so a rule author can inspect it. Each warning's wording sits in the prelude beside its rule.
- **Stages.** The `lint` stage reads only the outputs of earlier stages and never reaches into the expander.

### Prototype

Branch `design-lint-rfc-prototype`, commit `021ad8158`, not pushed, implements this option with `unused-binding` alone. Its fixtures under `tests/fixtures/lint/` are `unused_let`, `underscore_let`, `macro_introduced_let`, `macro_input_let`, `closure_reads_let`, `quote_only_let`, `empty_program` and `reads_in_every_form`. Each reports as intended.

### Cost

Instructions are measured on local-profile builds with `valgrind --tool=callgrind`, against `knave check` of the same build. Memory is measured with the binary's own `--counters` flag, built with `--features counters`, which reports the allocator's `peak_live_bytes` and `allocated_bytes` on any command. CI's `cargo xtask bench` runs only `knave emit`, so it cannot measure `knave lint`.

The instruction column measures the prototype's recursive walk, written as `(concat (f (first forms)) (g (rest forms)))`. The rise in instructions runs from +36 % to +73 %, and the largest absolute rise is +508 M, on `many_modules`. Nearly all of it is that interpreted walk: with the binder comparisons removed, the walk alone costs 1,905 M of the 1,906 M on `many_modules`. The flat table removes most of the walk, because Rust visits the nodes and each rule makes one loop over a table. That saving is not measured. Expanding `prelude/lint` alone costs 2.3 M instructions, and `knave check` costs the same with and without the prototype, within 0.7 %.

The recursive walk's `concat` copying also causes the allocation column, such as +131.6 MiB on `deep_nesting`. The flat table allocates each fact once, so allocation grows linearly with a definition's size. The lint stage frees what it allocates before `check` reaches its own peak, so the peak live heap rises only on the two smallest entries, where the rule program itself is the largest allocation.

On `deep_nesting`, the peak resident memory still rises by 3.4 MiB, and that rise is not heap. Running `valgrind --tool=massif --stacks=yes` on the local-profile prototype with `deep_nesting.knv` shows the peak stack rising from 0.55 MB under `knave check` to 2.53 MB under `knave lint`, so about 1.9 MiB is stack from the recursive walk. The remaining 1.5 MiB is unexplained. The flat table removes that recursion.

The owner's decisions name 24 knave rules. This projection is not measured. Each rule makes one loop over the table of each definition, so the cost grows with the rule count times the table's length, at a few interpreter steps per entry. Rules on the forms as read loop over a second table, the source as written.

### Stages

One `lint` stage lives in `src/lint/` and follows `ownership` in `DesignRules::STAGE_ORDER`. It reads `Program` for the knave rules and `TypedProgram` for the Rust rules. Each Rust rule is one struct behind one `Lint` trait: `unreachable-arm`, `missing-bang`, `flag-argument`, the `?` suffix rule and `needless-clone`.

A Rust rule reads data, never another stage's internals:

- **`unreachable-arm`:** `types` records each unreachable arm in `TypedProgram`, as the arm's pattern span and the span of the arm that covers it. `MatchCoverage` writes the record, in the first pull request of the `TypeChecker` design, and the `lint` stage turns each record into the warning.
- **`missing-bang`:** `ChangingFunctionNames::check` already reads only `&TypedProgram`. The one internal it touches is the ownership-private `WholeValueChanges`. The same fix applies: `ownership` records the facts in its output first, and the rule reads them.

Once the RFC 0063 interpreter, item 385 of the project's plan, runs macro code over checked code, rules run on it too, so the compiler keeps one interpreter. `knave lint` then checks `prelude/lint` on each run, and that check is the price of the design. It cannot be measured until RFC 0063 checks compile-time code.

### Host groups

Decision 5 of the `Expander` design splits `CompileTimeHost` into six traits: `ModuleQueries`, `DefinitionQueries`, `ModuleNotes`, `NameComparison`, `ExpansionCallbacks` and `SourceQueries`. It puts `global_value`, which the interpreter calls for every global, in `ExpansionCallbacks`. A lint run needs only part of that.

Every built-in a rule calls reaches one group or none:

| Built-in | Group |
|---|---|
| a rule's own definitions, read as globals | `global_value` |
| `same-binding?` | `NameComparison` |
| `introducing-macro`, `form-location` | `SourceQueries` |
| `warn` | `report_warning` |
| `first`, `rest`, `list`, `concat`, `prepend`, `len`, `empty?`, `nth`, `take`, `drop`, `symbol?`, `list?`, `string?`, `number?`, `keyword?`, `symbol-name`, `sorted-names`, `string`, `string-strip-prefix`, `value-eq`, `bool-not`, `number-add`, `number-sub`, `number-lt`, `number-le`, `number-gt`, `number-ge` | none |

Two options serve this.

**Amend decision 5**, for the project owner, with the seventh pull request of the `Expander` split:

- `global_value` moves into a group of its own, `GlobalValues`. The group changes state, because `global_value` takes `&mut self` and lowers and evaluates a global on its first use.
- `report_warning` forms a second added group, `Warnings`, which changes state too.
- The interpreter takes one `&mut dyn Host`. Each accessor of `Host` returns an optional group, such as `fn global_values(&mut self) -> Option<&mut dyn GlobalValues>`, with a default of `None`. A built-in calls the accessor of its group, and on `None` the interpreter reports one shared diagnostic. The refusal is written once, and no host writes a stub. The lint host returns `GlobalValues`, `NameComparison`, `SourceQueries` and `Warnings`. `Expander` can return each `&mut` group in turn, because a built-in holds only one borrow at a time.
- The RFC 0063 interpreter accepts the same `Host`.

**Keep the six groups.** The lint host implements all six. It answers the methods rules need and refuses every other method with one shared diagnostic. Both options write that diagnostic once, so they differ by about twenty one-line methods that refuse, not by twenty diagnostics.

| | Amend decision 5 | Keep the six groups |
|---|---|---|
| Decision 5 | changes: two more groups | unchanged |
| Lint host | implements four groups, no refusals | implements six groups, about 20 methods refuse |
| Refusal | one diagnostic, reported by the interpreter | one diagnostic, returned by about twenty one-line methods |
| Interpreter signature | one `&mut dyn Host` with optional groups | unchanged |
| Cost on `macro_heavy` | estimated at about 0.5 % | none |
| A missing group | a refusal at run time | a compile error |

The cost of the amendment is estimated, not measured, because the split does not exist yet. The estimate assumes about 10 instructions per host call for the accessor's indirect call and its `None` test. `knave check` on `macro_heavy` makes 617,935 host calls, which gives about 6 M of 1,185.7 M, about 0.5 %. `global_value` carries 603,088 of those calls, so its path is the one to keep cheap.

The build adds a unit test that `Expander` returns `Some` from every accessor, so the run-time refusal never reaches a macro.

Recommendation: amend decision 5. A host then implements only what it answers, and the refusal is stated once, so a later host such as the RFC 0063 interpreter's adds no stubs either.

**Docstring rules.** `CoreModule` holds each module's exports as `exports`, a list of bindings, so the read-back carries them as data and no rule needs `ModuleQueries`. `Program` holds no docstrings: they are module notes, kept by the expander's `ModuleNotes` and not handed out. The docstring rules therefore read docstrings from the forms as read, where a definer's docstring sits as written. They use the prelude's own docstring helpers, so the compiler still learns nothing about how a definer places its docstring.

### Built-ins

- **`warn`.** One built-in, shared with macros. It takes the description parts of `fail` and a required `:rule` name. As `fail` derives a code from its `:code` name, `warn` derives the code from the rule name, so `:rule unused-binding` gives L0801. The rule name travels on the `Diagnostic` as a value object with a public reader. `warn` calls `report_warning`, which takes a finished `Diagnostic`. Because a macro can call `warn`, every command that prints a warning applies the `lints` section, not only `knave lint`.
- **`introducing-macro`.** A built-in in `SourceQueries` that names the macro whose expansion introduced a form. It lands after `warn`. A rule uses it to leave out a binding that a macro wrote, which the user cannot fix.

### Rules at run time

- **Limits.** A rule runs once per definition, under `StepBudget::DEFAULT_LIMIT`, 30,000,000 steps, the budget of one top-level macro call, renewed for each definition and each rule. The walk has no other limit: `recur` rebinds the arguments and loops at the same interpreter depth (`expand/src/interpret/mod.rs:234-243` at `021ad8158`), so a table of any length runs in constant depth. The Rust read-back recurses, but it runs on the front-end stack that already serves 1,024 levels of nesting.
- **A rule that passes its budget.** The linter skips that rule for that definition and prints a `note:` on the user's definition that names the rule and says it was not checked. It never prints an error, never points into `prelude/lint.knv`, and never changes the exit code.
- **Policy.** Which heads are decision forms, the `_` prefix and every threshold live in `prelude/lint.knv`. A rule derives a decision-form depth from the table's parent indices in one loop. Rust collects only facts that hold for every rule, so it restates no prelude fact.
- **`unused-binding`.** It lists the names a definition reads with `sorted-names`. A binder whose name is absent is unread with no binding comparison, and `same-binding?` runs only against reads of the binder's own name.
- **Tests.** The build adds two fixtures under `tests/fixtures/lint/`: one definition nested 1,024 levels deep, and one call of 4,000 arguments. Each holds one unread binding, and `knave lint` exits 0 and prints its L0801 warning.
- **Forms as read.** A new object in `src/cli/`, extracted from `Terminal`, owns the `SourceMap`. It hands the `SourceMap` to the `lint` stage as a constructor argument, so the stage depends on no CLI type. `Program` does not carry the forms as read.
- **Two views of one definition.** A rule pairs an expanded definition with the top-level form that its expansion started from. The pairing cannot use spans alone, because `pinned-at` can place a definition's span outside its top-level form. The expander therefore records, on each definition in its output, the span of the top-level form it came from. That output is work for the expander.
- **Heads of forms as read.** A rule on forms as read matches heads by name, because those forms carry no binding. A user function named `when` therefore counts as a decision form for `nesting-depth`. The owner ruled out a shadowing lint, so the rule accepts that miscount.
- **The `_` prefix.** It silences only `unused-binding`.
- **Macro code.** `defmacro` bodies and `defrule` clauses become read-only data in the expander's output, in a shape agreed once the macro table becomes `MacroDefinitions`. Until then, macro code is not linted.
- **Locals a macro introduced.** `BindingInfo` in the `BindingArena` that `Program` carries gains the mark, extending the existing `is_introduced` set, which marks only globals today. Until then, a rule reads it from the macro origins.
- **Thresholds.** Each rule's default threshold lives in `prelude/lint.knv` beside the rule.
- **One printer.** `knave expand` prints the read-back forms, and a rule's table flattens the same forms. The read-back is then the only statement of how core IR reads as forms, and a rule author sees what a rule sees.

### Codes

L0801 `unused-binding`, L0803 `unreachable-arm` and L0804 `missing-bang`. L0802 is held for `unmatched-link`, pending Q-d. Later codes are assigned in the order rules are claimed. `docs/diagnostics.md` gains an `L08xx` row for lints.

### Q-a. Which commands run which rules

| Option | What `check` and `build` print | Cost of `check` | What a CI job writes |
|---|---|---|---|
| A: only `knave lint` runs any lint | No lint. L0434 and L0504, which users see today, move to `knave lint` only. | unchanged | `knave lint` |
| B: `check` also runs the knave rules | Every lint | +36 % to +73 %, up to +508 M instructions, with the prototype's recursive walk | `knave check` |
| C: `check` and `build` run the Rust rules only | `unreachable-arm`, `missing-bang`, `flag-argument`, the `?` suffix rule and `needless-clone`, under `lints` | unchanged for the two that exist today | `knave lint` |

Under C, `flag-argument` is a size rule, on by default, so a project with a `bool` parameter gets a warning on every `knave build` until it writes `(lints (flag-argument allow))` or removes the parameter.

Recommendation: C. Users keep the warnings they see today, and the knave rules run only where the owner placed them, in `knave lint`.

### Q-b. Which warnings `lints` can silence

- Only the `L08xx` lints.
- Every warning, the six of today included.

Recommendation: only lints. L0217, L0249, L0251 and L0256 report configuration problems that a user fixes rather than tolerates, and the owner's decision already makes L0434 and L0504 lints.

### Q-c. A `deny` level and the exit code

The owner decided that `lints` takes `allow` and thresholds. The question is whether it also takes `deny`, which turns a lint into an error, so the command exits 1.

- With `deny`, a project writes `(lints (unused-binding deny))` in `project.knv`, and CI runs `knave lint`.
- Without it, `knave lint` exits 0 on every warning, and CI needs a command-line flag such as `--deny-warnings`.

If `deny` exists, it either applies in every command that prints the lint, `build` and `run` included, or only in `knave lint`. In every command, a denied lint stops `knave run` during development, until the user fixes it. Only in `knave lint`, `deny` means one thing in CI and another at the prompt.

Recommendation: `deny`, applying in every command that prints the lint, with `knave lint` exiting 0 when it finds only warnings. One meaning per level is the uniform rule. A user writes `deny` knowingly, so a stopped `knave run` is the behavior they chose. A project then sets its CI strictness in `project.knv`, and no command-line flag is needed.

### Q-d. The code of `unmatched-link`

The doc generator warns about an unmatched `[name]` link as `unmatched-link`. That warning is new work, not yet on `main`.

- It takes L0802 and can be silenced through `lints`, as every other lint.
- It takes a code of the stage that reports it, and cannot be silenced.

Recommendation: L0802. The owner's decision on L0434 and L0504 already gives those two warnings `L08xx` codes, though other stages report them. The trade-off: a code's first digit no longer names the stage that reports it, so `docs/language.md` and `docs/diagnostics.md` must say that lint codes cross stages.

### Q-e. Whether `xtask bench` measures `knave lint`

The CI gate on `allocated_bytes` and `peak_live_bytes` measures only `knave emit`, so nothing gates the cost of `knave lint`. Should `xtask bench` measure `knave lint` too?

Recommendation: yes. The rules run in the interpreter on every definition, so a slow rule reaches every user, and only a gate catches it before release.

## Decision

The project owner decided these rules on 2026-11-11:

- Lint rules are knave code in a tool module `prelude/lint` that `prelude.knv` never imports, loaded only by `knave lint`. Rust keeps a thin host and the lints that need types or ownership.
- Lint codes use the range `L08xx`.
- A user silences a lint with a `_` prefix, or project-wide with a `lints` section in the project file, such as `(lints (unused-binding allow))`. There is no inline form.
- There is no shadowing lint.
- L0434 and L0504 become named `L08xx` lints, silenced like every lint, with no alias for the old codes.
- Size rules and their defaults: `module-lines` 150, `function-lines` 15, `function-arguments` 3, `flag-argument` 0 (typed, in Rust), and `nesting-depth` 3, which counts only decision forms (`if`, `when`, `unless`, `cond`, `match`, `let-match`, `let-try`), never closures, `let` or calls.
- A threshold lives in the `lints` section beside its rule, as `(lints (function-lines 20) (unused-binding allow))`.
- Size rules and simplification rules measure the source as written, not the expanded code, so rules receive the forms as read as well as the expanded program. Size rules are on by default.
- Later rules: simplifications (`(if c true false)`, `(not (not x))`, and `prefer-template` for a list built mostly of quoted pieces), kebab-case names, and a `?` suffix on a function that returns `bool` (typed). The prelude itself is not linted yet.
- More later rules. Correctness: `identical-branches`, `self-comparison`, `unused-value`, `loop-without-recur` and `missing-body`. Redundancy: `redundant-do`, `redundant-let` and `fn-wrapper`. Simplification: `if-to-when`, `not-to-unless`, `compare-to-bool` and `def-fn`. A typed `needless-clone` rule, in Rust. There is no `constant-condition`, `cyclomatic-complexity` or `comment-ratio` rule.
- No lint rule repeats a problem that the compiler or the formatter already reports.
- The linter owns the docstring rules: `missing-docstring` on an exported definition, `blank-docstring` and `missing-summary-line`. The linter has no rule for an unmatched `[name]` link, because the doc generator warns about it.

The choice among the options, the host-group amendment, and Q-a to Q-e wait for the project owner.

## Why not the other options

- **Forms captured during expansion:** it changes the expander, and it cannot answer `same-binding?` after expansion, because `Program` does not hand out the binding table.
- **A data view of the core IR:** it adds a value kind and built-ins that only lint rules use, and gives rules a second shape of code beside forms.
