# RFC 0069: `knave lint`

**Status:** Proposed
**Date:** 2026-11-11

## Problem

A program can bind a name that nothing reads, write `(if c true false)`, or grow a function past what a reader can hold in mind, and the compiler says nothing. Rustc's own lints never reach the user, because `knave build` passes `--cap-lints allow`. Two checks exist as Rust warnings, L0434 for an unreachable arm and L0504 for a missing `!`, but no user can silence either.

The language needs a command that runs such checks, written in knave where knave can express them, with one way to silence each check.

The project owner has decided:

- Lint rules are knave code in a tool module `prelude/lint` that `prelude.knv` never imports, loaded only by `knave lint`. Rust keeps a thin host and the lints that need types or ownership.
- Lint codes use the range `L08xx`.
- A user silences a lint with a `_` prefix, or project-wide with a `lints` section in the project file, such as `(lints (unused-binding allow))`. There is no inline form.
- There is no shadowing lint.
- L0434 and L0504 become named `L08xx` lints, silenced like every lint, with no alias for the old codes.
- Size rules and their defaults: `module-lines` 150, `function-lines` 15, `function-arguments` 3, `flag-argument` 0 (typed, in Rust), and `nesting-depth` 3, which counts only decision forms (`if`, `when`, `unless`, `cond`, `match`, `let-match`, `let-try`), never closures, `let` or calls.
- A threshold lives in the `lints` section beside its rule, as `(lints (function-lines 20) (unused-binding allow))`.
- Size rules and simplification rules measure the source as written, not the expanded code, so rules receive the forms as read as well as the expanded program. Size rules are on by default.
- Later rules: simplifications (`(if c true false)`, `(not (not x))`, and `prefer-template` for a list built mostly of quoted pieces), kebab-case names, and a `?` suffix on a function that returns `bool` (typed). The prelude itself is not linted yet.
- More later rules. Correctness: `identical-branches`, `self-comparison`, `unused-value`, `loop-without-recur` and `missing-body`. Redundancy: `redundant-do`, `redundant-let` and `fn-wrapper`. Simplification: `if-to-when`, `not-to-unless`, `compare-to-bool` and `def-fn`. A typed `needless-clone` rule, in Rust. There is no `constant-condition`, `cyclomatic-complexity` or `comment-ratio` rule.
- No lint rule repeats a problem that the compiler or the formatter already reports.
- The linter owns the docstring rules: `missing-docstring` on an exported definition, `blank-docstring` and `missing-summary-line`. An unmatched `[name]` link is not a lint rule, because the doc generator reports it as `unmatched-link`.

## Options

Each option runs after expansion and reads only the `Program` that `Expander::expand` returns. The options differ in the form a rule receives the expanded program in.

The example is the first rule, `unused-binding`:

```lisp
(defn area (width height)
  (let (unused (+ width 1))
    (* width height)))
```

Every option prints the same warning, and `knave lint` exits 0:

```text
warning[L0801]: `unused` is never read
 --> area.knv:2:9
  |
2 |   (let (unused (+ width 1))
  |         ^^^^^^ bound here and never read
  |
  = help: remove the binding, or name it `_unused` to keep it
```

### Read-back forms

The lint stage turns each definition of the program's modules back into kernel forms, the forms `knave expand` prints. Each symbol that names a binding carries that binding's identity, so the existing `same-binding?` compares two symbols by the binding that expansion resolved. A kernel form's head refers to no binding. A rule is a plain knave function that walks forms with `first`, `rest` and `symbol?`, as a macro does.

```lisp
(def area (fn (width height) (do (local unused (add width 1)) (mul width height))))
```

A rule also receives each module's forms as read, before expansion, for the size and simplification rules:

```lisp
(lint-module read expanded)
```

The lint stage expands `prelude/lint` as a program of its own and runs the rules in the compile-time interpreter, through a host of its own.

### Forms captured during expansion

The expander records every form at the moment it becomes a kernel form, with its scopes, and the rules read that record.

```lisp
(local unused (+ width 1))
```

The forms keep the user's names, but `same-binding?` needs the expander's binding table, which `Program` does not hand out after expansion. Capturing the forms changes the expander, and every `knave check` holds a second copy of the program in memory.

### A data view of the core IR

The interpreter gains a value that wraps a node of the core IR, and built-ins such as `core-kind`, `core-children` and `core-binding` that read it.

```lisp
(core-kind node)
```

The view loses nothing, but it adds a value kind and about six built-ins to the interpreter, which the RFC 0063 interpreter must carry too. Rules would also read a second shape of code that no macro uses.

## Recommendation

Read-back forms.

- **Small compiler, big prelude.** Rules stay knave code in `prelude/lint`, as the owner decided. The Rust side only reads, converts and reports.
- **Few rules, no exceptions.** A rule reads forms, the one data type for code, with the built-ins a macro uses, and `same-binding?` keeps its meaning.
- **User experience first.** A rule sees what `knave expand` prints, so a rule author can inspect it. Each warning's wording sits in the prelude beside its rule.
- **Stages.** The lint stage reads only the outputs of earlier stages and never reaches into the expander.

The design:

- **Stages.** The stage `lint` follows `expand` in `DesignRules::STAGE_ORDER`. The stage `typed_lint` follows `ownership` and reads `TypedProgram`. Each Rust rule is one struct behind one `Lint` trait. The Rust rules are `unreachable-arm`, `missing-bang`, `flag-argument`, the `?` suffix and `needless-clone`.
- **Host.** The lint stage's host implements only the groups of the split `CompileTimeHost` that rules need, and it never stubs a method.
- **`warn`.** One built-in, shared with every other caller. It takes the description parts of `fail` and a required `rule` symbol. The rule travels on the `Diagnostic` as a value object with a public reader. `warn` calls one narrow host method, `report-warning`, which takes a finished `Diagnostic` and sits in its own small group, so a host other than `Expander` can implement it. A warning stays a warning in its `Diagnostic`. The linter turns a denied warning into an error.
- **`introducing-macro`.** A built-in in the `SourceQueries` group that names the macro whose expansion introduced a form. It lands after `warn`. A rule uses it to leave out a binding that a macro wrote, which the user cannot fix.
- **Forms as read.** A new object, extracted from `Terminal`, owns the `SourceMap` and hands it to the linter. `Program` does not carry the forms as read.
- **Macro code.** `defmacro` bodies and `defrule` clauses become read-only data in the expander's output, in a shape agreed once the macro table becomes `MacroDefinitions`. Until then, macro code is not linted.
- **Locals a macro introduced.** The mark goes on `Bindings` once that object exists. Until then, a rule reads it from the macro origins.
- **Codes.** L0801 `unused-binding`, L0802 `unmatched-link` (reported by the doc generator), L0803 `unreachable-arm` and L0804 `missing-bang`. Later codes are assigned in the order rules are claimed.
- **Thresholds.** Each rule's default threshold lives in `prelude/lint.knv` beside the rule.

A prototype of this option with the `unused-binding` rule alone reported each of six example programs correctly. It added under 0.1 s over `knave check` on every corpus entry.

## Decision

The project owner decided the rules listed under Problem on 2026-11-11. The choice among the options and the unresolved questions below wait for the project owner.

## Unresolved questions

- **Which commands show lint warnings.**
  - A: only `knave lint`.
  - B: `knave check` also runs the knave rules.
  - C: `knave check` and `knave build` show only the Rust lints, and every warning can be silenced through `lints`.
- **The exit code of `knave lint` on a warning.** It always exits 0 now, with `--deny-warnings` added later, or it exits nonzero on a warning.

## Rejected options and why

- **Forms captured during expansion:** it changes the expander, costs memory in every `knave check`, and cannot answer `same-binding?` after expansion, because `Program` does not hand out the binding table.
- **A data view of the core IR:** it adds a value kind and built-ins that only lint rules use, and gives rules a second shape of code beside forms.

## Rule

The build that implements this RFC adds the section Lints to `docs/language.md`, which then states the rule.
