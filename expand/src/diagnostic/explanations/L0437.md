A `try` of a result in a function that returns a result with a different error
type makes the compiler emit a Rust `impl From`, which wraps the value's error
in a variant of the function's error type. That type must be an enum that the
program defines, without type parameters, with exactly one variant whose single
positional payload, not a box, has the type of the value's error. This error
reports a `try` where no such variant exists, such as when the function's error
is a `string`, a Rust type, an enum of the prelude, or a generic enum, or when
no variant has that payload. It also reports two or more variants that could
hold the value's error.

A function without a `type` signature takes the error of its first `try` as its
own error, so a second `try` with a different error reports this error too.

A `try` of a result in a function whose result is not a result reports `L0428`.

## Erroneous example

```lisp
(type total (fn ((ref str) (ref str)) (result i64 string)))

(defn total (left right)
  (ok (+ (try (parse left)) (try (parse right)))))

(defn main () (println (unwrap-ok (total "1" "2"))))
```

## Fixes

Give `total` an error enum whose `bad-number` variant takes a `parse` error:

```lisp
(defenum input-error (bad-number (parse-error i64)))

(type total (fn ((ref str) (ref str)) (result i64 input-error)))

(defn total (left right)
  (ok (+ (try (parse left)) (try (parse right)))))

(defn main () (println (unwrap-ok (total "1" "2"))))
```

Or keep `string` as the error, and build its text with `map-err`:

```lisp
(type total (fn ((ref str) (ref str)) (result i64 string)))

(type number (fn ((ref str)) (result i64 string)))

(defn number (text)
  (map-err (parse text) (fn (problem) (str "bad number: " problem))))

(defn total (left right)
  (ok (+ (try (number left)) (try (number right)))))

(defn main () (println (unwrap-ok (total "1" "2"))))
```
