An associated type, such as `parse-error` of `from-str`, takes its value from
the implementor of its trait, so applying it to a type parameter, as
`(parse-error target)` does, has a meaning only when the `where` that binds the
parameter bounds it by that trait. This error reports such an application whose
parameter lacks that bound, in any written type, such as a `type` signature,
the `where` of a `rust` form, the value clause of a `deftrait` entry, a struct
field, an enum payload or a trait method's signature. A bound that names another
trait, such as `(target ord)`, does not count. In a trait method's signature,
`(parse-error self)` reports this error even when the trait lists `from-str` as
a supertrait.

A struct or enum cannot bound its own type parameters, `L0417`, so a field or
payload type that applies an associated type to one of them always reports this
error: write a concrete type there, such as `(parse-error i64)`. An associated
type applied to a known type that does not implement the trait, such as
`(parse-error (vec i64))`, reports `L0451` instead.

## Erroneous example

```lisp
(type read-value
  (where (target)
    (fn ((ref str))
      (result target (parse-error target)))))

(defn read-value (text) (parse text))

(defn main ()
  (let ((count (result i64 _)) (read-value "4"))
    (println (unwrap-ok count))))
```

## Fixes

Give `target` the trait that owns `parse-error`:

```lisp
(type read-value
  (where ((target from-str))
    (fn ((ref str))
      (result target (parse-error target)))))

(defn read-value (text) (parse text))

(defn main ()
  (let ((count (result i64 _)) (read-value "4"))
    (println (unwrap-ok count))))
```

Or read one concrete type:

```lisp
(type read-count
  (fn ((ref str))
    (result i64 (parse-error i64))))

(defn read-count (text) (parse text))

(defn main () (println (unwrap-ok (read-count "4"))))
```
