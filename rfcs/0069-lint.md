# RFC 0069: `knave lint`

**Status:** Proposed
**Date:** 2026-11-11

## Problem

A program can bind a name that nothing reads, write `(if c true false)`, or grow a function past what a reader can hold in mind, and the compiler says nothing. Rustc's own lints never reach the user, because `knave build` passes `--cap-lints allow`. The compiler prints six warnings today, and no user can silence any of them:

- L0434: an unreachable `match` arm, from `types`.
- L0504: a function that changes an argument but whose name lacks `!`, from `ownership`.
- L0217, L0249, L0251 and L0256: a second Rust path for one trait, a macro input set aside, a library that hides a local module, and a test module that hides a source module, all from `expand`.

Q-b under Recommendation asks which of them a user can silence.

The language needs a command that runs style and correctness checks, written in knave where knave can express them, with one way to silence each check.

## Options

Each option runs after expansion and reads only the `Program` that `Expander::expand` returns. The options differ in the form in which a rule receives the expanded program.

The example is the first rule, `unused-binding`:

```lisp
(defn area (width height)
  (let (unused (+ width 1))
    (* width height)))
```

Every option prints the same warning:

```text
warning[L0801]: `unused` is never read
 --> area.knv:2:9
  |
2 |   (let (unused (+ width 1))
  |         ^^^^^^ bound here and never read
  |
  = help: remove the binding, or name it `_unused` to keep it
```

### Read-back forms

The `lint` stage turns each definition of the program's modules back into kernel forms:

```lisp
(def area (fn (width height) (do (local unused (add width 1)) (mul width height))))
```

The stage gives each binding one fresh scope that no expansion used, and puts that scope on every symbol that names the binding, so the existing `same-binding?` compares two symbols by the binding that expansion resolved. A kernel form's head names no binding.

The Rust read-back already visits every node, so it hands each definition to the rules as a flat table, one entry per node. An entry holds the node's form beside its facts: its parent's index and its depth, and for a symbol, whether it binds or reads and, for a binder, how many reads its binding has. The form carries the head, the span and the binding identity. A rule loops over the table with `loop` and `recur`, at constant interpreter depth. At an entry, it matches the form locally with `first` and `rest` to a fixed depth, as a macro does, and compares whole subtrees with `value-eq`, which recurses in Rust. Forms share structure, so the entries add no copy of the definition.

### Forms captured during expansion

The expander records every form at the moment it becomes a kernel form, with its scopes, and the rules read that record.

```lisp
(local unused (+ width 1))
```

The forms keep the user's names. But `same-binding?` needs the expander's binding table, which `Program` does not hand out after expansion, and the capture changes the expander.

### A data view of the core IR

The interpreter gains a value that wraps a node of the core IR, and built-ins such as `core-kind`, `core-children` and `core-binding` that read it.

```lisp
(core-kind node)
```

The view loses nothing, and a rule could loop over it as over a table. But it adds a value kind and about six built-ins to the interpreter, which the RFC 0063 interpreter must carry too, and a rule matches a node through those built-ins instead of with `first` and `rest`, so rules read a second shape of code that no macro uses.

## Recommendation

Read-back forms.

- **Small compiler, big prelude.** Rules stay knave code in `prelude/lint`. The Rust side only reads, converts and reports.
- **Few rules, no exceptions.** Every table entry holds a form, the one data type for code, and a rule matches it with the built-ins a macro uses. `same-binding?` keeps its meaning. The table adds only facts no form states: parent, depth and role.
- **Every accepted program lints.** No knave code recurses over the tree, so the walk has no limit tied to nesting or width.
- **User experience first.** The forms in a rule's table are what `knave expand` prints, so a rule author can inspect them. Each warning's wording sits in the prelude beside its rule.
- **Stages.** The `lint` stage reads only the outputs of earlier stages and never reaches into the expander.

### Prototype

Branch `design-lint-rfc-prototype`, not pushed, implements this option with `unused-binding` alone. Commit `021ad8158` walks nested forms recursively, commit `c763a16fd` hands the rule a flat table of forms, and commit `d52c01c95` records each binder's read count in the table and reports a skipped rule as `rule-skipped`. Its fixtures under `tests/fixtures/lint/` are `unused_let`, `underscore_let`, `macro_introduced_let`, `macro_input_let`, `closure_reads_let`, `quote_only_let`, `empty_program` and `reads_in_every_form`. Each reports as intended.

The two large inputs come from these generators:

python3 -c 'import functools; print("(defn deep (x)\n  (let (unused 1)\n    " + functools.reduce(lambda b, _: f"(if true {b} 0)", range(1022), "x") + "))\n\n(defn main () (println (deep 1)))")'

Compared with commit `021ad8158`'s recursive walk, the flat table lowers the rise on every corpus entry: on `many_modules` it falls from +508 M to +283 M. On `deep_nesting`, allocation falls from +131.6 MiB to +19.5 MiB. On commit `c763a16fd`, `valgrind --tool=massif --stacks=yes` on `deep_nesting.knv` showed that the flat table also removes the recursive walk's stack rise: 0.59 MB under `check` against 0.66 MB under `lint`, down from 0.55 MB against 2.53 MB. Expanding `prelude/lint` alone costs 2.3 M instructions, and `knave check` costs the same with and without the prototype, within 0.7 %.

The flat table allocates each fact once, so allocation grows linearly with a definition's size. The lint stage frees what it allocates before `check` reaches its own peak, so the peak live heap rises only where the rule program or the table is the largest allocation.

#### The worst case

A rule's worst case is a definition with many binders. Two chains measure it, each with one unread `unused`: the chain `(local v1 (+ v0 1)) (local v2 (+ v1 2)) ...`, and the shadowed chain `(local x (+ x 1))` repeated. `knave check` rejects either chain above 11,875 locals with L0326, because the definition's expansion does not finish, so 11,800 is the largest size measured.

| Input | `check` instructions | `lint` instructions | `check` wall time | `lint` wall time | Allocated over `check` | `lint` result |
|---|---|---|---|---|---|---|
| chain, 1,000 locals | 520 M | 678 M (+30 %) | 0.07 s | 0.11 s | +22.6 MiB | exit 0, L0801 |
| chain, 4,000 locals | 2,055 M | 2,672 M (+30 %) | 0.35 s | 0.49 s | +88.2 MiB | exit 0, L0801 |
| chain, 11,800 locals | 6,037 M | 7,844 M (+30 %) | 0.91 s | 1.25 s | +261.8 MiB | exit 0, L0801 |
| shadowed, 1,000 locals | 1,117 M | 1,275 M (+14 %) | 0.21 s | 0.19 s | +22.6 MiB | exit 0, L0801 |
| shadowed, 4,000 locals | 8,450 M | 9,065 M (+7 %) | 1.09 s | 2.16 s | +88.2 MiB | exit 0, L0801 |
| shadowed, 11,800 locals | 55,386 M | 57,190 M (+3 %) | 8.50 s | 8.62 s | +261.8 MiB | exit 0, L0801 |

The chains come from this generator, with `n` the number of locals:

```sh
python3 -c 'n = 11800; print("(defn chain (v0)\n  (local unused 0)\n" + "".join(f"  (local v{i} (+ v{i - 1} 1))\n" for i in range(1, n + 1)) + f"  v{n})\n\n(defn main () (println (chain 1)))")'
```

The rise grows linearly with the chain's length, so the rule is linear in its table. On the chain of 11,800 locals, the table holds 82,612 entries, and `unused-binding` spends 8,402,994 steps, about 102 per entry and 28 % of its budget of 30,000,000. The rule's own time there is about 0.34 s, the gap between `lint` and `check`. The budget would last for about 295,000 entries, and no definition that `knave check` accepts comes near that, so `unused-binding` finishes on every accepted program. Its limit is the compiler's own: a definition of at most 11,875 locals, linted in about 0.34 s.

Every rule must be linear in its table. The build tests that with the chain of 4,000 locals: a rule that compares every binder with every read passes its budget near 950 locals, while a linear rule lints the chain within 10 % of its budget.

The lint gate's first baseline comes from the build of this design, not from the prototype.

The owner's decisions name 24 knave rules. This projection is not measured. If each rule cost what `unused-binding` costs on the worst case, linting the chain of 11,800 locals would take about 24 times 0.34 s, near 8 s, beside 0.9 s for `knave check`, and about 24 times 1,807 M, near 43 G instructions. Rules on the forms as read loop over a second table, the source as written.

### Stages

One `lint` stage lives in `src/lint/` and follows `ownership` in `DesignRules::STAGE_ORDER`. It reads `Program` for the knave rules and `TypedProgram` for the Rust rules. Each Rust rule is one struct behind one `Lint` trait: `unreachable-arm`, `missing-bang`, `flag-argument`, the `?` suffix rule and `needless-clone`.

A Rust rule reads data, never another stage's internals:

- **`unreachable-arm`:** `types` records each unreachable arm in `TypedProgram`, as the arm's pattern span and the span of the arm that covers it. `MatchCoverage` writes the record, in the first pull request of the `TypeChecker` design, and the `lint` stage turns each record into the warning.
- **`missing-bang`:** `ChangingFunctionNames::check` already reads only `&TypedProgram`. The one internal it touches is the ownership-private `WholeValueChanges`. The same fix applies: `ownership` records the facts in its output first, and the rule reads them.

Once the RFC 0063 interpreter, item 385 of the project's plan, runs macro code over checked code, rules run on it too, so the compiler keeps one interpreter. `knave lint` then checks `prelude/lint` on each run, and that check is the price of the design. It cannot be measured until RFC 0063 checks compile-time code.

### Host groups

On `main`, commit `6eceb3d0c` splits `CompileTimeHost` into six traits: `ModuleQueries`, `DefinitionQueries`, `ModuleNotes`, `NameComparison`, `ExpansionCallbacks` and `SourceQueries`. `CompileTimeHost` is their union, and each built-in reaches only its own group, but the interpreter still takes one `&mut dyn CompileTimeHost`. `global_value`, which the interpreter calls for every global, sits in `ExpansionCallbacks` beside `expand_call`, `set_macro_step_limit`, `declare_definition` and `require_module`. Pull request 474, in review, adds a `Warnings` trait with `report_warning` as one more supertrait of `CompileTimeHost`.

Every built-in a rule calls reaches one group or none:

| Built-in | Group on `main` | Group after the amendment |
|---|---|---|
| a rule's own definitions, read as globals | `ExpansionCallbacks` | `GlobalValues` |
| `same-binding?` | `NameComparison` | `NameComparison` |
| `introducing-macro`, `form-location` | `SourceQueries` | `SourceQueries` |
| `warn` | `Warnings` | `Warnings` |
| `first`, `rest`, `list`, `concat`, `prepend`, `len`, `empty?`, `nth`, `take`, `drop`, `symbol?`, `list?`, `string?`, `number?`, `keyword?`, `symbol-name`, `string`, `string-strip-prefix`, `value-eq`, `bool-not`, `number-add`, `number-sub`, `number-lt`, `number-le`, `number-gt`, `number-ge` | none | none |

On `main`, a lint host implements every group of `CompileTimeHost`. It answers `global_value`, `NameComparison`, `SourceQueries` and `report_warning`. It refuses 16 methods: the 6 of `ModuleQueries`, the 4 of `DefinitionQueries`, the 2 of `ModuleNotes`, and the 4 of `ExpansionCallbacks` other than `global_value`.

**The amendment**, for the project owner:

- `global_value` moves out of `ExpansionCallbacks` into a group of its own, `GlobalValues`. The group changes state, because `global_value` takes `&mut self` and lowers and evaluates a global on its first use.
- The interpreter takes one `&mut dyn Host`. Each accessor of `Host` returns an optional group, such as `fn global_values(&mut self) -> Option<&mut dyn GlobalValues>`, with no default body. A built-in calls the accessor of its group, and on `None` the interpreter reports one shared diagnostic. `Expander` can return each `&mut` group in turn, because a built-in holds only one borrow at a time.
- The lint host returns `GlobalValues`, `NameComparison`, `SourceQueries` and `Warnings`, and `None` for the other four groups, so it writes no `ExpansionCallbacks` stub.
- The RFC 0063 interpreter accepts the same `Host`.

| | `main` as it stands | Accessors with a default | Accessors with no default |
|---|---|---|---|
| Groups | six, plus `Warnings` | adds `GlobalValues` | adds `GlobalValues` |
| Lint host | implements every group, 16 methods refuse | implements four groups | implements four groups and writes eight accessors, four returning `None` |
| Refusal | one diagnostic, returned by 16 one-line methods | one diagnostic, reported by the interpreter | one diagnostic, reported by the interpreter |
| Interpreter signature | `&mut dyn CompileTimeHost` | `&mut dyn Host` with optional groups | `&mut dyn Host` with optional groups |
| Cost on `macro_heavy` | none | estimated at about 0.5 % | estimated at about 0.5 % |
| A forgotten group | a compile error | a refusal at run time | a compile error |

The cost of the accessors is estimated, not measured, because they do not exist yet. The estimate assumes about 10 instructions per host call for the accessor's indirect call and its `None` test. `knave check` on `macro_heavy` makes 617,935 host calls, which gives about 6 M of 1,185.7 M, about 0.5 %. `global_value` carries 603,088 of those calls, so its path is the one to keep cheap.

The build adds a unit test that `Expander` returns `Some` from every accessor, so the run-time refusal never reaches a macro.

Recommendation: move `global_value` into `GlobalValues`, and give `Host` optional accessors with no default. A compile error catches a forgotten group, at a cost of about eight one-line methods per host, the refusal is stated once in the interpreter, and the lint host refuses no method.

**Docstring rules.** `CoreModule` holds each module's exports as `exports`, a list of bindings, so the read-back carries them as data and no rule needs `ModuleQueries`. `Program` holds no docstrings: they are module notes, kept by the expander's `ModuleNotes` and not handed out. The docstring rules therefore read docstrings from the forms as read, where a definer's docstring sits as written. They use the prelude's own docstring helpers, so the compiler still learns nothing about how a definer places its docstring.

### Built-ins

- **`warn`.** One built-in, shared with macros. It takes the description parts of `fail` and a required `:rule` name. As `fail` derives a code from its `:code` name, `warn` derives the code from the rule name, so `:rule unused-binding` gives L0801. The rule name travels on the `Diagnostic` as a value object with a public reader. `warn` calls `report_warning`, which takes a finished `Diagnostic`. Because a macro can call `warn`, every command that prints a warning applies the `lints` section, not only `knave lint`.
- **`introducing-macro`.** A built-in in `SourceQueries` that names the macro whose expansion introduced a form. It lands after `warn`. A rule uses it to leave out a binding that a macro wrote, which the user cannot fix.

### Rules at run time

- **Limits.** A rule runs once per definition, under `StepBudget::DEFAULT_LIMIT`, 30,000,000 steps, the budget of one top-level macro call, renewed for each definition and each rule. The walk has no other limit: `recur` rebinds the arguments and loops at the same interpreter depth (`expand/src/interpret/mod.rs`, lines 231 to 252 on `main`), so a table of any length runs in constant depth. The Rust read-back recurses, but it runs on the front-end stack that already serves 1,024 levels of nesting.
- **A rule that passes its budget.** The linter skips that rule for that definition and reports the lint `rule-skipped`, L0805, once per definition, naming every skipped rule, such as ``warning[L0805]: `unused-binding` was not checked in `build-table` ``. It has the standard layout, with its label on the user's definition, and never points into `prelude/lint.knv`. `(lints (rule-skipped allow))` silences it, and a project that writes `deny` makes CI fail instead of passing silently.
- **Policy.** Which heads are decision forms, the `_` prefix and every threshold live in `prelude/lint.knv`. A rule derives a decision-form depth from the table's parent indices in one loop. Rust collects only facts that hold for every rule, so it restates no prelude fact.
- **`unused-binding`.** It makes one pass over the table and reports a `local` binder whose read count is 0. Rust counts the reads, because binding identity is a fact Rust already resolves. The `_` prefix and the leaving out of macro-introduced binders stay in the prelude.
- **Tests.** The build adds three fixtures under `tests/fixtures/lint/`: one definition nested as deep as `knave check` accepts, one call of 4,000 arguments, and the chain of 4,000 locals. Each holds one unread binding, and `knave lint` exits 0 and prints its L0801 warning. No input `knave check` accepts drives a linear rule past its budget, so the `rule-skipped` path is tested with a step budget of 10.
- **Forms as read.** A new object in `src/cli/`, extracted from `Terminal`, owns the `SourceMap`. It hands the `SourceMap` to the `lint` stage as a constructor argument, so the stage depends on no CLI type. `Program` does not carry the forms as read. Rules receive the forms as read as a flat table too, with the same entries but no binding identity.
- **Two views of one definition.** A rule pairs an expanded definition with the top-level form that its expansion started from. The pairing cannot use spans alone, because `pinned-at` can place a definition's span outside its top-level form. The expander therefore records, on each definition in its output, the span of the top-level form it came from. That output is work for the expander.
- **Heads of forms as read.** A rule on forms as read matches heads by name, because those forms carry no binding. A user function named `when` therefore counts as a decision form for `nesting-depth`. The owner ruled out a shadowing lint, so the rule accepts that miscount.
- **The `_` prefix.** It silences only `unused-binding`.
- **Macro code.** `defmacro` bodies and `defrule` clauses become read-only data in the expander's output, in a shape agreed once the macro table becomes `MacroDefinitions`. Until then, macro code is not linted.
- **Locals a macro introduced.** `BindingInfo` in the `BindingArena` that `Program` carries gains the mark, extending the existing `is_introduced` set, which marks only globals today. Until then, a rule reads it from the macro origins.
- **Thresholds.** Each rule's default threshold lives in `prelude/lint.knv` beside the rule.
- **One printer.** `knave expand` prints the read-back forms, and a rule's table holds the same forms. The read-back is then the only statement of how core IR reads as forms, and a rule author sees what a rule sees.

### Codes

L0801 `unused-binding`, L0803 `unreachable-arm`, L0804 `missing-bang` and L0805 `rule-skipped`. L0802 is held for `unmatched-link`, pending Q-d. Later codes are assigned in the order rules are claimed. `docs/diagnostics.md` gains an `L08xx` row for lints.

### Q-a. Which commands run which rules

| Option | What `check` and `build` print | Cost of `check` | What a CI job writes |
|---|---|---|---|
| A: only `knave lint` runs any lint | No lint. L0434 and L0504, which users see today, move to `knave lint` only. | unchanged | `knave lint` |
| B: `check` also runs the knave rules | Every lint | +16 % to +65 %, up to +283 M instructions on the corpus | `knave check` |
| C: `check` and `build` run the Rust rules only | `unreachable-arm`, `missing-bang`, `flag-argument`, the `?` suffix rule and `needless-clone`, under `lints` | unchanged for the two that exist today | `knave lint` |

Under C, `flag-argument` is a size rule, on by default, so a project with a `bool` parameter gets a warning on every `knave build` until it writes `(lints (flag-argument allow))` or removes the parameter.

Recommendation: C. Users keep the warnings they see today, and the knave rules run only where the owner placed them, in `knave lint`.

### Q-b. Which warnings `lints` can silence

- Only the `L08xx` lints.
- Every warning, the six of today included.

Recommendation: only lints. L0217, L0249, L0251 and L0256 report configuration problems that a user fixes rather than tolerates, and the owner's decision already makes L0434 and L0504 lints.

### Q-c. A `deny` level and the exit code

The owner decided that `lints` takes `allow` and thresholds. The question is whether it also takes `deny`, which turns a lint into an error, so the command exits 1.

- With `deny`, a project writes `(lints (unused-binding deny))` in `project.knv`, and CI runs `knave lint`.
- Without it, `knave lint` exits 0 on every warning, and CI needs a command-line flag such as `--deny-warnings`.

If `deny` exists, it either applies in every command that prints the lint, `build` and `run` included, or only in `knave lint`. In every command, a denied lint stops `knave run` during development, until the user fixes it. Only in `knave lint`, `deny` means one thing in CI and another at the prompt.

Recommendation: `deny`, applying in every command that prints the lint, with `knave lint` exiting 0 when it finds only warnings. One meaning per level is the uniform rule. A user writes `deny` knowingly, so a stopped `knave run` is the behavior they chose. A project then sets its CI strictness in `project.knv`, and no command-line flag is needed.

### Q-d. The code of `unmatched-link`

The doc generator warns about an unmatched `[name]` link as `unmatched-link`. That warning is new work, not yet on `main`.

- It takes L0802 and can be silenced through `lints`, as every other lint.
- It takes a code of the stage that reports it, and cannot be silenced.

Recommendation: L0802. The owner's decision on L0434 and L0504 already gives those two warnings `L08xx` codes, though other stages report them. The trade-off: a code's first digit no longer names the stage that reports it, so `docs/language.md` and `docs/diagnostics.md` must say that lint codes cross stages.

## Decision

The project owner decided these rules on 2026-11-11:

- Lint rules are knave code in a tool module `prelude/lint` that `prelude.knv` never imports, loaded only by `knave lint`. Rust keeps a thin host and the lints that need types or ownership.
- Lint codes use the range `L08xx`.
- A user silences a lint with a `_` prefix, or project-wide with a `lints` section in the project file, such as `(lints (unused-binding allow))`. There is no inline form.
- There is no shadowing lint.
- L0434 and L0504 become named `L08xx` lints, silenced like every lint, with no alias for the old codes.
- Size rules and their defaults: `module-lines` 150, `function-lines` 15, `function-arguments` 3, `flag-argument` 0 (typed, in Rust), and `nesting-depth` 3, which counts only decision forms (`if`, `when`, `unless`, `cond`, `match`, `let-match`, `let-try`), never closures, `let` or calls.
- A threshold lives in the `lints` section beside its rule, as `(lints (function-lines 20) (unused-binding allow))`.
- Size rules and simplification rules measure the source as written, not the expanded code, so rules receive the forms as read as well as the expanded program. Size rules are on by default.
- Later rules: simplifications (`(if c true false)`, `(not (not x))`, and `prefer-template` for a list built mostly of quoted pieces), kebab-case names, and a `?` suffix on a function that returns `bool` (typed). The prelude itself is not linted yet.
- More later rules. Correctness: `identical-branches`, `self-comparison`, `unused-value`, `loop-without-recur` and `missing-body`. Redundancy: `redundant-do`, `redundant-let` and `fn-wrapper`. Simplification: `if-to-when`, `not-to-unless`, `compare-to-bool` and `def-fn`. A typed `needless-clone` rule, in Rust. There is no `constant-condition`, `cyclomatic-complexity` or `comment-ratio` rule.
- No lint rule repeats a problem that the compiler or the formatter already reports.
- The linter owns the docstring rules: `missing-docstring` on an exported definition, `blank-docstring` and `missing-summary-line`. The linter has no rule for an unmatched `[name]` link, because the doc generator warns about it.
- `xtask bench` measures `knave lint` too, held to the same 1 % gate on allocated and peak live bytes as `emit`.

The choice among the options, the host-group amendment, and Q-a to Q-d wait for the project owner.

## Why not the other options

- **Forms captured during expansion:** it changes the expander, and it cannot answer `same-binding?` after expansion, because `Program` does not hand out the binding table.
- **A data view of the core IR:** a flat walk needs no new value kind, because table entries hold forms. The view adds a value kind and built-ins that only lint rules use, and rules would match nodes through them instead of with `first` and `rest`.
