An associated type that a Rust trait declares is a type of one argument, the
implementor. `(parse-error i64)` is the error type of parsing an `i64`, because
the prelude's `from-str` lists `i64` with a `parse-error` clause. This error
reports such a type written with an argument that the trait's entries do not
cover, such as `(parse-error str)` or `(parse-error (vec i64))`, wherever the
type appears, such as a `type` signature, a field of a struct, an enum payload,
a `let` binding or a `the` form.

An argument that is a type parameter reports `L0453` instead when its `where`
does not bind the trait, and nothing when it does, as in `(where ((a from-str))
(fn (a) (parse-error a)))`. An argument that contains `_`, such as `_` or `(vec
_)`, is not checked here: inference fills it, and a call that needs the trait
reports its own error, such as `L0404` for `(the (result str (parse-error _))
(parse text))`.

An `impl` of such a trait for a struct of the program reports this error at a
method signature that applies the associated type to `self`, as `(negative
self)` does, because an `impl` cannot state an associated type of a Rust trait:
a `(type ...)` entry there reports `L0447`.

## Erroneous example

```knave
(type read-number
  (fn ((ref str))
    (result i64 (parse-error str))))

(defn read-number (text) (parse text))

(defn main ()
  (println (unwrap-ok (read-number "7"))))
```

## Fixes

Apply `parse-error` to the type that `parse` reads:

```knave
(type read-number
  (fn ((ref str))
    (result i64 (parse-error i64))))

(defn read-number (text) (parse text))

(defn main ()
  (println (unwrap-ok (read-number "7"))))
```
